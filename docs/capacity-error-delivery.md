# 容量错误交付与客户端画像稳定性

## 客户端画像

一次请求首次进入 Provider 时，冻结当时的公共客户端画像。后续同账号重试、
换账号以及 HTTP 回退继续使用该画像；下一次请求重新读取当前配置。
完整自定义 UA 和独立 Desktop 辅助画像一起保存，后台版本更新不改变在途请求。

这份快照不保存 Token、Cookie、安装编号或会话状态。账号切换仍按新账号
重新绑定私有身份，已有精确 WS 续接仍遵循原连接所有权。
TLS、HTTP/WS 选择、连接池、压缩、调度及重试预算未因此改变。

## 容量错误

仅在最终返回下游时，将 `server_is_overloaded` 和 `slow_down` 转成
`server_error`。通过 HTTP 错误响应路径返回时使用 503；以 SSE 事件交付
的失败仍保留流式响应状态，在流内发出失败事件，不能把已发出的 200 改为 503。
WS 错误包装中的数值状态改为 503。
内部原始错误、账号反馈、计费事实和重试决策不改写。

限流、额度耗尽、参数错误、`previous_response_not_found` 和
`websocket_connection_limit_reached` 不套用这项转换。非容量事件保持原交付规则。
Responses 与 Chat、流式与非流式入口均需覆盖；Chat 不能把转换后的状态
重新覆盖为上游原来的 429。

## 重试边界

503 或流内 `server_error` 只表达可重试失败，不保证 New API 或客户端会重试。
已经输出内容后，网关不自动重放请求。内部、New API 和客户端分别重试可能
叠加请求次数与等待时间，应结合下游重试配置评估，不能宣传为首字提速。
这项改动不新增账号冻结或追加内部容量重试次数。
