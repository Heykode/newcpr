# 官方更新合并核对清单

适用于官方功能移植、修复同步和“已对齐官方”的验收。先固定官方提交，不能把
最新分支、旧参考工作树和本次发布基线混为一谈。以用户批准的功能边界为准。

## 合并前

- 分别记录上次已合入的官方提交、本次官方目标提交、本地目标提交和当前部署源码；核对关联 PR 和预期行为。用固定提交区分上次漏接与官方后续修复，不把未部署的本地基线当成线上旧版本。
- 沿入口、共享 helper、执行器、交付和测试追踪调用链；不能只看 PR 改动文件。
- 对每个差异标记：原样移植、必要接入、用户排除、未完成。必要接入必须写明实际影响。
- 核对旧分支中的额外判断、兜底、错误映射和恢复逻辑；不能因为本地原来有就默认保留。
- 插件专属代码可以按批准边界排除；同文件中的原生协议规则和性能改进须单独评估。

## 差异归因与实际接入

在本次既有合并清单中记录每个受影响行为的官方落点、本地真实调用路径、保留差异及验证结果，不另建一套重复清单。

| 归因 | 判定依据 |
| --- | --- |
| 本地漏接或接错 | 上次固定官方基线已有该实现，本地实际入口、后端、错误出口或发行环境未接齐 |
| 本地遗留差异 | 旧适配仍与本次官方不同；单独说明已有用户需求、实际影响和保留理由。未复现故障不能直接称为已确认缺陷 |
| 官方旧版缺陷、后续修复 | 对比上次官方基线与修复提交，说明本地是否同样适用；不能计成上次漏合 |
| 官方仍有的行为或风险 | 指出官方当前源码和验证边界；不能把本地额外改法称作官方已提供的修复 |
| 新增功能或明确排除 | 记录对应提交、接入位置或既有排除依据；同提交的公共改动仍单独核对 |

- 官方真实作用代码及其调用关系是移植依据。优先直接采用可兼容的官方实现；不同后端确需适配时，逐项说明官方规则怎样落到运行路径，不能用口头“效果一样”替代源码和验证。
- 确认生产选择的实现：进程内队列测试不能代替 Redis 队列，原生入口不能代替 Excel/State 入口，HTTP 不能自动代表 WS，公共 helper 相同不能代表调用者已使用它。
- 错误必须从实际原因追到 Provider 分类、Core 重试、API 状态码/正文和下游消费方。内部诊断写了队满，不等于外部错误已正确；修改分类时一并核对恢复分支。
- 对保留的额外限制逐项核对作用范围：排队截止不自动等于请求终止，快照冲突次数不自动等于所有重查次数，执行并发不等于等待人数。按官方完整分支接入相关发送状态、换号预算和归属保护，不能只删除一个限制条件。
- 发布能力同时核对本仓库的实际索引、通道、权限与资产。不能把官方源码复制成功等同于自定义发行源可用，也不能把普通 CI 镜像部署标签当成已具备全部下载资产的正式发行。

## 规则维护与跨会话使用

- 本清单是共用合并规则入口，由仓库 `AGENTS.md` 引用；各层 `.trellis/spec/` 保存具体合同，版本差异账只保存当次证据。其他电脑、会话和接手人先拉取目标分支并阅读这些文件，不能依赖聊天记忆或本机任务日志。
- 改变实现合同的同一提交中替换相应旧条款、旧断言和过时夹具；无引用的专用辅助代码一起删除。不能让相互冲突的两套规则长期并存。
- 历史基线、单次任务限制和曾经通过的测试不是永久门禁；当前用户授权和本次固定官方代码决定边界。仍需保留的差异写明真实用途、运行影响和验证，不用“本地适配”四个字代替说明。
- 本清单不会让工具自动保证遵守；人工与 AI 评审须核对实际调用链、差异账和证据。保留既有 CI，不额外增加重复全量验证。

## 同步测试与规范

- 每次更新同时核对受影响的实现、测试、夹具和规范。验收依据是用户确认的需求与本次固定官方源码；本地旧测试、旧规范不能仅凭存在时间更早就成为保留旧行为的理由。
- 测试失败先确认原因：新版实现缺陷、官方行为已变、夹具不再符合真实接口，或验证环境不足。只有确认实现缺陷才修代码；已过时的预期、计数、字段和规范应在同一提交更新。
- 对仍需保留的本地差异，记录具体需求和运行影响，证明不会抵消已批准的官方更新。不能为满足旧断言恢复旧绑定时机、插队路径或其他已被替换的行为。
- 更新断言须有官方代码或已确认业务合同依据；不以删除失败用例、放宽结果或忽略错误代替修复。保留官方正反例及关键本地回归，避免重复验证同一行为。
- 旧迁移的“不改变其他数据”及幂等测试应固定所验证的迁移终点；跨版本升级测试则逐项核对新增字段及其默认值，再比较旧字段。不能让旧schema整行断言禁止新版本合法新增字段，也不能为通过断言删掉新迁移。
- 一次性合并、调试、回退和环境准备脚本不进入源码提交；删除失效或重复测试时同步清理其专属夹具。保留维护所需的差异账和验证结论，原始日志留在仓库外。
- 实施前定位与本次官方行为冲突的旧断言及规范；实施后在同一提交更新。历史“测试通过”只证明当时的预期得到执行，不能证明预期仍正确。核对清单也不能把尚未验证的接入标为完成。

## 验证矩阵

| 边界 | 至少核对什么 |
| --- | --- |
| 请求入口 | 鉴权顺序、解压、字段缺失/null、非法输入、转换后执行参数 |
| 正常输出 | 文本、工具、结构化结果、身份、真实 usage、流式和非流式 |
| 错误来源 | 入口拒绝、上游 HTTP 错误、wire 失败、缺终态、转换失败、提交/结算失败分别验证 |
| 客户端交付 | 状态码、完整正文、允许透传的头、Retry-After、首帧、终态与 DONE 次数 |
| 等待和取消 | 准入前、首事件前、首事件后；保活不得重建任务；断开只取消并释放一次 |
| 非流式汇总 | 错误事件与最终完整结果的优先级、同一响应身份、完成项缺口/冲突 |
| 共享代码 | 原生 Responses、HTTP/WS 和其他调用方的既有行为是否被牵连 |
| 实际后端 | 运行时选择的 Store/队列/协议适配器是否真正执行新代码；不能只验未使用的公共实现 |
| 调度与恢复 | 按受影响分支选取严格/优先/宽松、根/子线程、队满/超时、空闲候选、开关与换号次数；执行槽空闲但队列非空、独立截止及跨池限制分别核对 |
| 发行接入 | 自定义仓库的索引、通道与实际可安装资产一致；发布推进权限可用，正式发行与普通部署职责明确 |
| 验证边界 | 源码比较、模拟协议、真实数据库、真实上游分别记录；没有执行不能写“通过” |

发现缺陷时先证明新用例在旧代码下失败，再验证修复后通过。测试预期要来自固定
官方源码或独立参考实现，不能只复述当前本地代码。修复时删除已失效的专用 helper
和错误分支，保留官方同样存在的公共规则。

优先采用官方正反例，再补本地真实接入差异的最小必要用例。原始 helper 的隔离验证
只证明该 helper；没有覆盖真实调度与请求链时，不得宣称生产问题已完整复现或修复。
矩阵按本次影响选择，不要求每次全量排列组合；同一源码、环境与有效范围内的合格证据
可以复用。仅在代码、失败或未解决风险发生变化时追加检查，遵循既有 CI 和部署证据规则，
不为本清单增加重复全量测试、永久临时脚本或新的通用门禁。

## 验收与发布

- 将每个行为差异关联到来源、测试名称和结果；有未解释差异就不能声称全链路等价。
- 在用户指定环境执行相关测试、编译和检查，核对被验证文件与待发布源码一致。
- 报告完成项、保留差异、未执行验证和用户可见的兼容变化。官方通过 CI 不代替本地适配验证。
- 明确区分改正错误提示、恢复可用性和消除根因；例如状态码对齐不代表队首阻塞消失。未解释差异保留为未完成，不以笼统“全部对齐”结束验收。
- 提交、推送、合并、标签和部署分别记录状态，按本次授权执行。

Chat 的具体来源、允许适配和已执行验证见 [Chat 对齐记录](chat-official-parity.md)。
