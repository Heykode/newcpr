# 账号累计消费合同

## 范围与接口

账号详情新增长期累计统计，涉及数据库、Admin、API 和前端；不扩展官方额度和调度行为。

```rust
async fn load_account_cumulative_costs(
    &self,
    account_ids: &[String],
) -> AdminStoreResult<BTreeMap<String, Vec<AccountCumulativeCost>>>;
```

响应示例：`"cumulativeCosts":[{"currency":"USD","estimatedAmount":"105","estimatedAmountDisplay":"$105.00"}]`。
数据库主键为累计表 `(provider_account_ref, currency)` 和去重表 `request_id`。

## 统计独立性

- 账号视图 `usage` 仍是 `ProviderQuota::representative_window_usage` 给出的当前额度窗口，
  不可替换为历史累计，也不可用累计消费推算当前额度百分比或预计总额。
- `cumulativeCosts` 独立加载，按稳定账号 ID 和币种隔离。无有效费用返回空数组，
  真实零金额返回零；不得把未知费用、缺失额度或旧后端字段缺失展示成真实零消费。
- 同身份重复导入保留的账号 ID 继续关联累计。删号后新 ID 不按邮箱跨账号合并。

## 账务持久化

- `0006_account_cumulative_costs.sql` 创建累计表与 request_id 去重表。
- 只计已成功交付、具有费用证据的请求；HTTP 要求有效客户端成功状态，
  WebSocket 无单次 HTTP 状态时可凭成功终态和下游提交认定。
- 与 `completed_usage_fact_predicate` 共享成功交付边界：费用存在本身即为证据。
  SQL 三值逻辑必须显式转为真/假，缺失 HTTP 状态不得误计。
- 推理用量视图另行排除 OpenAI `prewarm`，但累计费用账本不按此分类减账。
  已交付预热的已知费用保留；未知费用不得伪造。窗口推理费用与永久累计可以不同，
  预测不回写账本，API Key 预算继续按执行器取得的费用结算。
- Repository 请求终态费用不可变，首次有效费用通过触发器与去重写入在同一事务累计。
  重复结束、晚到状态、并发请求和回滚必须通过真实 PostgreSQL 验证。
- 累计与去重表不受请求日志清理影响，清理后的同 request_id 重放也不得重复累计。
- 回填与触发器启用在迁移事务中以表锁衔接；仅能补算现存有效记录，不恢复已清理历史。

## 数值与部署

- 单次费用继续使用原 `DecimalAmount`；累计使用独立 `CumulativeCostAmount`，
  保留十位小数、支持三十位整数，对应累计列 `numeric(40,10)`。
- 不以浮点累加。极大累计超出共享格式化器容量时必须保留真实字符串，不能降级成零。
- 追加迁移不能改动已发布文件。SQLx 旧二进制缺少已应用迁移会拒绝启动：
  回滚应使用仍携带 0006 的兼容构建，保留累计表与去重数据。
- 本地测试使用 `CI=true` 和真实 PostgreSQL/Redis。全链路测试要求连接密码为
  48 位十六进制字符串；缺环境提前返回的“通过”不构成数据库验证。

## 验证与错误

| 输入或状态 | 合同 |
| --- | --- |
| 无金额证据 | 不累计；返回空数组，前端“暂无统计” |
| 成功费用为零 | 保存有效零费用，与未知区别 |
| 失败、未交付、HTTP 无成功状态 | 不累计，晚到成功状态可补计 |
| 已累计请求重复写入 | 不重复计入 |
| 负数、科学计数法、超 30 位整数或 10 位小数 | `InvalidCumulativeCostAmount` |
| 数据库查询失败 | 显式返回 Store 错误，不伪装为零 |

## 正常与边界用例

- 正常：100 + 重复导入 + 5，累计 105；窗口值不受影响。
- 边界：9999999999.9999999999 + 0.0000000001，累计 10000000000。
- 错误：HTTP 状态缺失不凭成功字符串直接计费；未知费用不填 0。

## 必需测试

- `provider_accounts/cumulative_costs.rs`：导入、额度清空、真正运行 retention、
  日志删除后重放、并发小数、回滚、迁移回填、账号/币种、零/未知、容量边界。
- Admin/API：窗口 5 和累计 100/105 独立；无额度仍保留累计；极大金额不显示为零。
- UI：桌面与 320/390 手机宽度，空字段、零金额、多币种、大金额不溢出。
- 预热交叉回归：首次插入就携带最终分类与费用；已知预热费用累计一次，
  未知费用不累计，二者均不进入推理窗口；日志清理和同 ID 重放不重复累计。
- 健康条和热度诊断仍保留预热的成功、失败与未完成次数，但推理 Token、
  费用及预测覆盖率排除预热；不要将完成用量筛选直接套在健康终态计数上。

## 预热历史分类的上线检查

- 新 OpenAI Provider 仅根据实际 `generate=false` 赋予 `prewarm` 分类，
  真实推理不能仅凭客户端元数据中的同名提示从推理视图中消失。
- 旧版本可能从客户端元数据直接保存 `request_kind=prewarm`；旧行只有该字段时，
  不能据此证明当时的 `generate` 值。上线前按授权只读核对历史分类的来源和数量，
  缺少证据应标记未知，不宣称生产已受影响，也不回写、删除或重算费用。
- 本次不新增分类标记或迁移，不修改已发布的 0006；费用事实保留与推理视图筛选
  是不同合同，不能为了消除展示差异而改动历史账本。

## 错误与正确

- 错误：查询所有未过期 `model_requests` 后直接称为永久累计。
- 正确：首次有效费用事务性写入独立累计表，保留 request_id 去重数据。
- 错误：用累计金额替代 `usage.costs`，让额度周期比例和累计账务混用。
- 正确：新增 `cumulativeCosts`，保持原窗口统计和推算字段不变。
